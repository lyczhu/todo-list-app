# Feature Specification: 待办事项管理

**Feature Branch**: `001-todo-management`

**Created**: 2026-10-10

**Status**: Draft

**Input**: User description: "开发一个待办事项管理功能。用户可以创建、查看、标记完成、删除待办事项。待办事项需要包含标题、描述和截止日期。列表按截止日期排序。"

## Clarifications

### Session 2026-10-10

- Q: 在「全部」分类视图中，"按状态区分"具体指什么呈现方式？ → A: 分区展示——列表分为「未完成」「已完成」两个区块，各区块内部按截止日期排序。
- Q: 用户打开待办列表时，默认显示哪个分类？ → A: 默认显示「未完成」分类。
- Q: 待办事项内容的编辑（修改标题/描述/截止日期）是否纳入本特性范围？ → A: 不纳入，编辑留待后续特性。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建与查看待办事项 (Priority: P1)

用户有一个待办事项管理界面。用户输入标题（可选填描述和截止日期）创建一条待办事项，保存后
该事项立即出现在列表中，并按截止日期排序展示——最紧急（截止日期最早）的事项排在最前面，
让用户一眼看到接下来该做什么。列表支持按状态分类查看：「未完成」「已完成」「全部」三个
分类可切换，默认打开「未完成」。

**Why this priority**: 创建与查看是待办管理的核心闭环；没有这一能力，其余操作（完成、删除）
都无从发生。仅此一条即可构成可用的最小产品。

**Independent Test**: 在空列表上连续创建多条不同截止日期的待办事项，验证列表完整展示所有事项
且顺序严格按截止日期升序排列，即可独立测试并交付价值。

**Acceptance Scenarios**:

1. **Given** 待办列表为空，**When** 用户输入标题"买牛奶"并保存，**Then** 列表出现"买牛奶"，
   处于未完成状态。
2. **Given** 用户正在创建新事项，**When** 用户填写标题、描述和截止日期后保存，**Then** 该事项
   以完整信息（标题、描述、截止日期）记录并展示。
3. **Given** 列表中已有截止日期分别为下月、明天、今天的事项，**When** 用户查看列表，**Then**
   事项按截止日期从早到晚排序（今天 → 明天 → 下月）。
4. **Given** 用户创建的待办未填写截止日期，**When** 保存成功，**Then** 该事项排在所有已设
   截止日期事项之后。
5. **Given** 用户打开待办列表，**When** 未做任何分类切换，**Then** 默认展示「未完成」分类，
   已完成事项不出现在该视图中。
6. **Given** 列表中存在未完成与已完成事项，**When** 用户切换到「已完成」分类，**Then** 仅展示
   已完成事项；切换到「全部」分类，**Then** 列表分为「未完成」「已完成」两个区块分区展示，
   各区块内部均按截止日期升序排序。

---

### User Story 2 - 标记完成与删除待办事项 (Priority: P2)

用户完成了一件事后，将对应待办标记为完成；该事项在列表中呈现明显的已完成状态（在默认「未
完成」视图中随即消失，可在「已完成」或「全部」分类中查看）。对于不再需要的事项，用户直接
删除，删除后该事项不再出现在任何分类中。

**Why this priority**: 完成与删除是清单"保持干净"的关键动作，依赖 P1 的存在，价值次之。

**Independent Test**: 先创建若干事项，再分别对其执行标记完成与删除操作，验证状态变化、分类
归属与列表更新符合预期，可独立测试。

**Acceptance Scenarios**:

1. **Given** 默认「未完成」视图中存在事项"交周报"，**When** 用户将其标记为完成，**Then**
   "交周报"从「未完成」视图消失，并出现在「已完成」分类及「全部」视图的已完成区块中，
   显示为已完成状态。
2. **Given** 列表中存在事项"过期的促销"，**When** 用户删除该事项并确认，**Then** 该事项从所有
   分类中彻底移除，刷新后也不再出现。
3. **Given** 用户误触删除，**When** 删除操作尚未确认，**Then** 用户可以取消，事项保持不变。

---

### User Story 3 - 逾期未办提醒 (Priority: P3)

用户打开列表时，截止日期已过但仍未完成的事项以醒目方式（如高亮/标注"已逾期"）呈现，帮助用户
优先处理拖延事项。

**Why this priority**: 提升体验的增值能力，不影响核心闭环，可延后交付。

**Independent Test**: 创建一条截止日期为昨天的未完成事项，打开列表验证其带有逾期标识；其余
事项不受影响。

**Acceptance Scenarios**:

1. **Given** 存在截止日期为昨天且未完成的事项，**When** 用户查看列表，**Then** 该事项显示
   逾期标识。
2. **Given** 存在截止日期为昨天的已完成事项，**When** 用户查看列表，**Then** 该事项不显示
   逾期标识。

---

### Edge Cases

- 标题为空或仅空白字符时创建：系统拒绝保存并提示"标题不能为空"。
- 标题/描述超长：按明确的长度上限校验（见假设）并给出可理解的提示。
- 截止日期早于今天（创建时即逾期）：允许创建，列表按逾期规则展示。
- 列表中存在多条截止日期相同的事项：以创建时间先后作为稳定次序。
- 并发/重复提交：连续快速点击保存不产生重复事项（以一次保存一条为准）。
- 删除最后一条事项后：列表显示有意义的空状态提示，而非空白页。
- 切换到的分类中没有任何事项：该分类显示空状态提示（如「已完成」为空时提示暂无已完成事项）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许用户创建待办事项，事项至少包含标题，并支持可选的描述和截止日期。
- **FR-002**: 系统 MUST 校验标题非空（去除空白后），拒绝无标题的事项并给出明确提示。
- **FR-003**: 系统 MUST 展示待办事项列表，每条事项可见其完成状态、标题、描述与截止日期。
- **FR-004**: 系统 MUST 支持按完成状态分类查看：「未完成」「已完成」「全部」三种分类可切换，
  默认展示「未完成」。
- **FR-005**: 在「全部」分类中，系统 MUST 将事项按状态分区展示（「未完成」区块在上、「已完成」
  区块在下），各区块内部均遵循 FR-006 的排序规则。
- **FR-006**: 系统 MUST 将列表（或分区内的每个区块）按截止日期升序排序；无截止日期事项排在
  有截止日期事项之后。
- **FR-007**: 系统 MUST 允许用户将未完成事项标记为完成；完成后该事项不再出现在「未完成」
  分类，可在「已完成」及「全部」的已完成区块中以已完成状态查看。
- **FR-008**: 系统 MUST 允许用户删除待办事项，删除后该事项不再出现在任何分类且持久生效。
- **FR-009**: 系统 MUST 持久保存待办事项，用户下次访问时数据不丢失。
- **FR-010**: 系统 MUST 对截止日期已过且未完成的事项给出逾期标识。
- **FR-011**: 系统 MUST 在列表（或某一分类/区块）为空时展示空状态引导（提示创建第一条事项
  或说明暂无该类事项）。

### Key Entities

- **待办事项 (Todo)**：用户记录的一件待完成的事。属性：标题（必填）、描述（可选）、截止日期
  （可选）、完成状态（未完成/已完成，用于分类查看与分区展示）、创建时间（用于同截止日期时的稳定排序）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从打开界面到成功创建一条含标题、描述、截止日期的事项耗时不超过 30 秒。
- **SC-002**: 列表中 100% 的事项（含「全部」视图各区块内）按截止日期升序呈现（无截止日期的
  在区块末尾），用户无需手动整理。
- **SC-003**: 用户标记完成或删除一条事项后，界面在 1 秒内反映最新列表状态。
- **SC-004**: 用户重新打开应用时，此前保存的事项 100% 完整恢复。
- **SC-005**: 用户切换「未完成」「已完成」「全部」分类后，展示内容与所选分类 100% 一致，且
  切换在 1 秒内完成。
- **SC-006**: 对 10 名首次使用者的可用性走查中，至少 90% 能在无指导下完成"创建→标记完成→
  在已完成分类中找回→删除"全流程。

## Assumptions

- 单用户场景：v1 不含账号体系与多人共享/协作，任何访问者操作同一份清单。
- 描述与截止日期为可选字段；标题为必填（依据功能描述将三者列为事项属性但仅标题为核心标识）。
- 标题长度上限 200 字符、描述上限 2000 字符为合理默认（未指定时采用业界常见清单类应用标准）。
- 列表按状态分类查看：「未完成」「已完成」「全部」；默认视图为「未完成」；「全部」视图采用
  未完成/已完成分区展示（见 Clarifications 与 FR-004/FR-005）。
- 编辑已创建事项的标题/描述/截止日期明确不在本特性范围内（见 Clarifications 2026-10-10），
  留待后续特性。
- 逾期判定以"截止日期 < 今天 且 未完成"为准。
- 数据保留：事项长期保留直至用户删除，无自动清理。
