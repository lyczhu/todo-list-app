# Feature Specification: 待办事项管理

**Feature Branch**: `001-todo-management`

**Created**: 2026-10-10

**Status**: Draft

**Input**: User description: "开发一个待办事项管理功能。用户可以创建、查看、标记完成、删除待办事项。待办事项需要包含标题、描述和截止日期。列表按截止日期排序。"

## Clarifications

### Session 2026-10-10

- Q: 在「全部」分类视图中，"按状态区分"具体指什么呈现方式？ → A: 分区展示——列表分为「未完成」「已完成」两个区块，各区块内部按截止日期排序。
- Q: 用户打开待办列表时，默认显示哪个分类？ → A: 默认显示「未完成」分类。
- Q: 待办事项内容的编辑（修改标题/描述/截止日期）是否纳入本特性范围？ → A: 不纳入，编辑留待后续特性。

### Session 2026-10-17

- Q: 在新增页保存成功后，应用应该自动返回首页，还是留在新增页继续添加？ → A: 保存成功后自动返回首页，列表已包含新事项。
- Q: 用户在新增页已有输入但未保存时选择返回，系统应该如何处理这些未保存内容？ → A: 弹出确认提示，用户可继续编辑或放弃并返回。
- Q: 如果用户点击"+"时首页正停留在「已完成」或「全部」分类，保存返回后首页应显示哪个分类？ → A: 自动切换到「未完成」分类，确保新事项立即可见。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建与查看待办事项 (Priority: P1)

应用默认落地首页（待办列表页），首页加载时展示待办列表。用户点击首页的"+"入口进入独立的
新增页，输入标题（可选填描述和截止日期）创建一条待办事项；保存成功后自动返回首页并切换到
「未完成」分类，该事项立即出现在列表中，并按截止日期排序展示——最紧急（截止日期最早）的
事项排在最前面，让用户一眼看到接下来该做什么。列表支持按状态分类查看：「未完成」「已完成」「全部」三个分类可
切换，默认打开「未完成」。

**Why this priority**: 创建与查看是待办管理的核心闭环；没有这一能力，其余操作（完成、删除）
都无从发生。仅此一条即可构成可用的最小产品。

**Independent Test**: 从首页点击"+"进入新增页，连续创建多条不同截止日期的待办事项，验证每次
保存后自动返回首页、列表完整展示所有事项且顺序严格按截止日期升序排列，即可独立测试并交付价值。

**Acceptance Scenarios**:

1. **Given** 首页待办列表为空，**When** 用户点击"+"进入新增页，输入标题"买牛奶"并保存，
   **Then** 应用自动返回首页，列表出现"买牛奶"，处于未完成状态。
2. **Given** 用户正在新增页创建新事项，**When** 用户填写标题、描述和截止日期后保存，**Then**
   应用自动返回首页，该事项以完整信息（标题、描述、截止日期）记录并展示。
3. **Given** 列表中已有截止日期分别为下月、明天、今天的事项，**When** 用户查看列表，**Then**
   事项按截止日期从早到晚排序（今天 → 明天 → 下月）。
4. **Given** 用户创建的待办未填写截止日期，**When** 保存成功，**Then** 该事项排在所有已设
   截止日期事项之后。
5. **Given** 用户打开应用，**When** 首页加载完成且未做任何分类切换，**Then** 落地首页并默认
   展示「未完成」分类的待办列表，已完成事项不出现在该视图中。
6. **Given** 列表中存在未完成与已完成事项，**When** 用户切换到「已完成」分类，**Then** 仅展示
   已完成事项；切换到「全部」分类，**Then** 列表分为「未完成」「已完成」两个区块分区展示，
   各区块内部均按截止日期升序排序。
7. **Given** 用户停留在「已完成」分类，**When** 用户点击"+"进入新增页并保存成功，**Then**
   应用自动返回首页、切换到「未完成」分类，新事项在列表中可见。

---

### User Story 2 - 标记完成与删除待办事项 (Priority: P2)

用户完成了一件事后，将对应待办标记为完成；该事项在列表中呈现明显的已完成状态（在默认「未
完成」视图中随即消失，可在「已完成」或「全部」分类中查看）。对于不再需要的事项，用户直接
删除，删除后该事项不再出现在任何分类中。

**Why this priority**: 完成与删除是清单"保持干净"的关键动作，依赖 P1 的存在，价值次之。

**Independent Test**: 先创建若干事项，再分别对其执行标记完成与删除操作，验证状态变化、分类
归属与列表更新符合预期，可独立测试。

**Acceptance Scenarios**:

1. **Given** 默认「未完成」视图中存在事项"交周报"，**When** 用户将其标记为完成，**Then**
   "交周报"从「未完成」视图消失，并出现在「已完成」分类及「全部」视图的已完成区块中，
   显示为已完成状态。
2. **Given** 列表中存在事项"过期的促销"，**When** 用户删除该事项并确认，**Then** 该事项从所有
   分类中彻底移除，刷新后也不再出现。
3. **Given** 用户误触删除，**When** 删除操作尚未确认，**Then** 用户可以取消，事项保持不变。

---

### User Story 3 - 逾期未办提醒 (Priority: P3)

用户打开列表时，截止日期已过但仍未完成的事项以醒目方式（如高亮/标注"已逾期"）呈现，帮助用户
优先处理拖延事项。

**Why this priority**: 提升体验的增值能力，不影响核心闭环，可延后交付。

**Independent Test**: 创建一条截止日期为昨天的未完成事项，打开列表验证其带有逾期标识；其余
事项不受影响。

**Acceptance Scenarios**:

1. **Given** 存在截止日期为昨天且未完成的事项，**When** 用户查看列表，**Then** 该事项显示
   逾期标识。
2. **Given** 存在截止日期为昨天的已完成事项，**When** 用户查看列表，**Then** 该事项不显示
   逾期标识。

---

### Edge Cases

- 标题为空或仅空白字符时创建：系统拒绝保存并提示"标题不能为空"。
- 标题/描述超长：按明确的长度上限校验（见假设）并给出可理解的提示。
- 截止日期早于今天（创建时即逾期）：允许创建，列表按逾期规则展示。
- 列表中存在多条截止日期相同的事项：以创建时间先后作为稳定次序。
- 并发/重复提交：连续快速点击保存不产生重复事项（以一次保存一条为准）。
- 删除最后一条事项后：列表显示有意义的空状态提示，而非空白页。
- 切换到的分类中没有任何事项：该分类显示空状态提示（如「已完成」为空时提示暂无已完成事项）。
- 新增页已有未保存输入时选择返回/取消：弹出确认提示；用户可继续编辑并停留在新增页，或确认
  放弃输入并返回首页（不创建事项、不保留草稿）。
- 后端不可用或请求失败（网络错误、5xx）：界面展示错误提示与重试路径，列表区不白屏，创建/
  完成/删除入口在失败恢复前禁用（FR-012）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许用户创建待办事项，事项至少包含标题，并支持可选的描述和截止日期。
- **FR-002**: 系统 MUST 校验标题非空（去除空白后），拒绝无标题的事项并给出明确提示。
- **FR-003**: 系统 MUST 展示待办事项列表，每条事项可见其完成状态、标题、描述与截止日期。
- **FR-004**: 系统 MUST 支持按完成状态分类查看：「未完成」「已完成」「全部」三种分类可切换，
  默认展示「未完成」。
- **FR-005**: 在「全部」分类中，系统 MUST 将事项按状态分区展示（「未完成」区块在上、「已完成」
  区块在下），各区块内部均遵循 FR-006 的排序规则；此处“系统”含前端渲染层——后端按契约返回带
  `completed` 字段的已排序全量数据，分区呈现由前端完成（与 contracts §GET /todos 一致）。
- **FR-006**: 系统 MUST 将列表按截止日期升序排序——含「全部」视图内的「未完成」与「已完成」
  每一个区块各自独立遵循本规则；无截止日期事项排在有截止日期事项之后。
- **FR-007**: 系统 MUST 允许用户将未完成事项标记为完成；完成后该事项不再出现在「未完成」
  分类，可在「已完成」及「全部」的已完成区块中以已完成状态查看。
- **FR-008**: 系统 MUST 允许用户删除待办事项，删除后该事项不再出现在任何分类且持久生效。
- **FR-009**: 系统 MUST 持久保存待办事项，用户下次访问时数据不丢失。
- **FR-010**: 系统 MUST 对截止日期已过且未完成的事项给出逾期标识：包含可读文案「已逾期」，
  且与未逾期事项存在可区分的视觉强调（颜色/加粗/底色任选其一即可，不锁定具体色值），使验收
  可判定“可区分且含可读文案”。
- **FR-011**: 系统 MUST 在列表（或某一分类/区块）为空时展示空状态引导（提示通过首页"+"创建
  第一条事项，或说明暂无该类事项）。
- **FR-012**: 系统 MUST 在后端请求进行中提供可见的加载反馈，并在请求失败（含后端不可用）时
  展示可理解的错误提示；错误状态下页面不得白屏，提交类操作入口暂时禁用以防重复无效请求，
  用户可重试（如刷新列表或重新提交）。
- **FR-013**: 系统 MUST 以首页（待办列表页）作为默认落地页，首页加载时即展示待办列表；首页
  MUST 提供“+”入口，点击后进入独立的新增页；“+”为导航操作，不属 FR-012 所述提交类入口，
  不因错误态禁用。
- **FR-014**: 新增页保存成功后，系统 MUST 自动返回首页、切换到「未完成」分类，并展示包含
  新事项的最新列表。
- **FR-015**: 新增页存在未保存输入（标题/描述/截止日期任一非空）时，返回操作（含应用内返回
  与浏览器/系统返回键）MUST 先给出确认提示；用户可继续编辑，或放弃输入并返回首页（放弃不创建
  事项、不保留草稿）。
- **FR-016**: 系统 MUST 在删除待办事项前弹出可取消的确认；用户取消则事项保持不变，仅在确认后
  才执行删除（与 US2-AC2/AC3 一致）。

### Key Entities

- **待办事项 (Todo)**：用户记录的一件待完成的事。属性：标题（必填）、描述（可选）、截止日期
  （可选）、完成状态（未完成/已完成，用于分类查看与分区展示）、创建时间（用于同截止日期时的稳定排序）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从首页点击"+"进入新增页，到成功创建一条含标题、描述、截止日期的事项并
  返回首页看到该事项，耗时不超过 30 秒。
- **SC-002**: 列表中 100% 的事项（含「全部」视图各区块内）按截止日期升序呈现（无截止日期的
  在区块末尾），用户无需手动整理。
- **SC-003**: 用户标记完成或删除一条事项后，界面在 1 秒内反映最新列表状态。
- **SC-004**: 用户重新打开应用时，此前保存的事项 100% 完整恢复。
- **SC-005**: 用户切换「未完成」「已完成」「全部」分类后，展示内容与所选分类 100% 一致，且
  切换在 1 秒内完成。
- **SC-006**: 对 10 名首次使用者的可用性走查中，至少 90% 能在无指导下完成"创建→标记完成→
  在已完成分类中找回→删除"全流程。

## Assumptions

- 单用户场景：v1 不含账号体系与多人共享/协作，任何访问者操作同一份清单。
- 首页（待办列表页）为默认落地页；创建待办在独立的新增页完成，保存成功后自动返回首页并
  切换到「未完成」分类（见 Clarifications 2026-10-17 与 FR-013/FR-014）。
- 描述与截止日期为可选字段；标题为必填（依据功能描述将三者列为事项属性但仅标题为核心标识）。
- 标题长度上限 200 字符、描述上限 2000 字符为合理默认（未指定时采用业界常见清单类应用标准）。
- 列表按状态分类查看：「未完成」「已完成」「全部」；默认视图为「未完成」；「全部」视图采用
  未完成/已完成分区展示（见 Clarifications 与 FR-004/FR-005）。
- 编辑已创建事项的标题/描述/截止日期明确不在本特性范围内（见 Clarifications 2026-10-10），
  留待后续特性。
- 逾期判定以"截止日期 < 今天 且 未完成"为准；其中"今天"以**服务端本地日期（服务器时钟）**
  为基准（见 research R3），不以客户端时区判定，避免跨时区偏差（决策 CHK010）。
- 数据保留：事项长期保留直至用户删除，无自动清理。
- 术语对照（决策 F2）：本文「分类」＝前端 store 的分类状态（`filter`/`currentCategory`）＝
  API 查询参数 `status`（取值 active/completed，缺省为全部）。
- 允许同名/重复标题事项：标题无唯一性约束，事项以自增 `id` 为唯一键（决策 CHK020）。
- 可访问性（键盘全流程操作、读屏语义/ARIA）在 v1 明确**不在本特性范围内**，不构成本特性
  验收项（决策 CHK006）；如后续纳入需另立特性。
